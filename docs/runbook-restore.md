# Restore runbook

What to do when something is lost. In every scenario the original files in S3 are the source of truth: the database is an index of them, and it can be rebuilt.

## What protects what

| Layer                                                                                     | Protects against                     | Where                                                      |
| ----------------------------------------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------- |
| S3 (11 nines durability, 3+ availability zones)                                           | Disk and hardware failure            | `users/{userId}/originals/…`                               |
| S3 versioning + 30-day noncurrent retention                                               | Accidental overwrite or delete       | Older versions of the same key                             |
| App IAM policy: deleting only adds a delete marker; versions can't be deleted             | A leaked app key wiping the archive  | `memory-vault-app` user                                    |
| S3 Object Lock, governance mode, 30 days (from M3)                                        | Anyone deleting a version early      | Every object version written since it was turned on        |
| Trash: 30 days in the app before anything is deleted                                      | Deleting the wrong photo             | Trash page; `assets.deleted_at`                            |
| Object metadata on every original (`sha256`, `source`, `original-path`, `original-mtime`) | Losing the database                  | Each object's `x-amz-meta-*` headers                       |
| Nightly catalogue export                                                                  | Losing the database                  | `system/catalog/{userId}/latest.jsonl.gz` (+ dated copies) |
| Nightly `pg_dump`                                                                         | Losing the database                  | `system/db-backups/daily/…`, `system/db-backups/monthly/…` |
| Weekly integrity check                                                                    | Silent drift between database and S3 | `system/integrity/{date}.json`                             |
| Optional cross-region replica                                                             | Losing a whole AWS region            | Second bucket (off by default; see the setup guide)        |

## 1. Restore the database from a backup

1. List backups (with an admin profile):

   ```bash
   aws s3 ls s3://BUCKET/system/db-backups/daily/ --profile <admin>
   ```

2. Download the newest:

   ```bash
   aws s3 cp s3://BUCKET/system/db-backups/daily/2026-11-24.dump ./vault.dump --profile <admin>
   ```

3. Restore into an empty database (local Docker shown; use the RDS endpoint in production):

   ```bash
   docker compose up -d postgres
   docker compose exec -T postgres dropdb -U vault --if-exists vault_restored
   docker compose exec -T postgres createdb -U vault vault_restored
   docker compose exec -T postgres pg_restore -U vault -d vault_restored --no-owner < vault.dump
   ```

4. Point `DATABASE_URL`/`DATABASE_MIGRATE_URL` at `vault_restored`, run `pnpm --filter @memory-vault/api db:migrate`, then `pnpm vault-admin integrity`. Place names are part of the dump; if a dump predates them, run `pnpm vault-admin load-places`.
5. Anything uploaded after the dump is picked up automatically: the integrity check lists it as "unrecorded in S3", and the S3 event consumer adopts originals from their own metadata. Old SQS messages are kept for 14 days.

## 2. Rebuild the index without any database backup

Every original carries its SHA-256, source and original path as object metadata, and the catalogue export lists every location of every file.

1. Start from an empty, migrated database (`pnpm --filter @memory-vault/api db:migrate`).
2. Find the user ID: it is the folder name under `users/` in the bucket.
3. Rebuild:

   ```bash
   pnpm vault-admin rebuild-index --user-id <uuid> --email you@example.com
   ```

   This re-creates the account with the same ID (new password, authenticator and recovery codes), adopts every original from its own metadata, then restores every other location from the newest catalogue export. Thumbnails are regenerated by the worker.

4. Run `pnpm vault-admin integrity` to confirm.
5. Load place names again (they are reference data, not in the catalogue): `pnpm vault-admin load-places`.

## 3. Recover a deleted or overwritten object

Within 30 days, an older version still exists:

```bash
aws s3api list-object-versions --bucket BUCKET --prefix users/{userId}/originals/ab/abcdef… --profile <admin>
aws s3api copy-object --bucket BUCKET --key users/{userId}/originals/ab/abcdef….jpg \
  --copy-source "BUCKET/users/{userId}/originals/ab/abcdef….jpg?versionId=VERSION" --profile <admin>
```

Removing a delete marker (`aws s3api delete-object … --version-id <marker-id>`) also brings the object back.

## 3b. Recover a file deleted from Trash

Something deleted from Trash (after its 30 days, or with **Delete now**) still exists as an older version for 30 more days.

**If you still have the file**, the easiest way is to upload it again: **Upload anyway** in the browser, or `pnpm vault upload <source> --include-deleted`.

**Otherwise:**

1. Find its SHA-256. Each one is recorded when it is deleted:

   ```bash
   docker compose exec postgres psql -U vault -d vault \
     -c "SELECT original_name, sha256, purged_at FROM deleted_content ORDER BY purged_at DESC LIMIT 20;"
   ```

   The same name and SHA-256 are in the `asset.purged` events in `audit_events`.

2. Remove the delete marker on the original, with your admin profile (the app's key can't):

   ```bash
   aws s3api list-object-versions --bucket BUCKET \
     --prefix users/{userId}/originals/ab/abcdef… --profile <admin>
   # In "DeleteMarkers", the one with "IsLatest": true:
   aws s3api delete-object --bucket BUCKET --key users/{userId}/originals/ab/abcdef….jpg \
     --version-id <marker VersionId> --profile <admin>
   ```

3. Let the app adopt it again. This re-adds anything in the bucket that the index is missing, makes its previews again, and clears its "deleted by you" record:

   ```bash
   pnpm vault-admin rebuild-index --user-id {userId}
   ```

   If the last nightly catalogue still listed it as being in Trash, it comes back in Trash: restore it from there.

## 4. Export everything

While the API runs, `pnpm vault export /path/to/folder` does all of this for you: every original in its original folders, with its name and date, each checked against its SHA-256, plus a `catalogue.json` and a README. It resumes if interrupted.

Without the app, from S3 alone: originals are named by content hash. To get the original folder layout and names back:

```bash
aws s3 cp s3://BUCKET/system/catalog/{userId}/latest.jsonl.gz . --profile <admin>
aws s3 sync s3://BUCKET/users/{userId}/originals/ ./originals --profile <admin>
gunzip -c latest.jsonl.gz | tail -n +2 | python3 -c '
import json, os, shutil, sys
for line in sys.stdin:
    item = json.loads(line)
    source = os.path.join("originals", item["s3Key"].split("/originals/", 1)[1])
    for location in item["locations"]:
        target = os.path.join("export", location)
        os.makedirs(os.path.dirname(target), exist_ok=True)
        shutil.copy2(source, target)
'
```

Files with `takenAt` and `origins[].modifiedAt` keep their original timestamps in the catalogue if you need to restore them with `touch -d`.

## 5. Check health at any time

```bash
pnpm vault-admin integrity      # database ↔ S3, both directions
pnpm vault report --verify      # every scanned source file ↔ S3, with safe-to-delete lists
```

Rehearse sections 1 and 4 once a year so the steps stay familiar.
